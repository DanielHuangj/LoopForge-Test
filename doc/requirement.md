## 1. 目标与价值

### 1.1 目标

建设一个供公司内部员工使用的 Web 订餐网站，提供两项核心能力：

1. 员工可查看已开放的每日菜单（含菜品图片）、选择菜品并提交订单，也可查看和取消自己的订单。
2. 菜品管理员可维护菜品及其图片，创建和发布每日菜单，并将临时无法供应的菜品标记为售罄。

### 1.2 价值

- 将线下收集订餐需求改为线上下单，减少漏单、错单和重复统计。
- 以系统菜单和价格作为唯一信息源，降低口头传达造成的菜品、价格不一致。
- 通过菜品图片帮助员工快速识别菜品，降低选错菜品的概率。
- 保留提交时的订单明细与价格快照，为对账和争议处理提供依据。
- 通过角色隔离，避免员工接触菜单维护能力，也避免菜品管理员查看员工订单。

本期以第 6 节全部验收标准通过作为 MVP 完成判定，不另设无法验证的主观指标。

## 2. 用户与角色

| 角色 | 身份与使用场景 | 权限边界 |
| --- | --- | --- |
| 未登录访问者 | 尚未完成企业身份认证的人员 | 只能看到登录入口并完成企业统一登录；不能查看菜单、价格、订单或后台数据。 |
| 普通员工 | 公司内部需要订餐的员工 | 可查看处于开放窗口内的已发布菜单；可加入、修改、移除购物车菜品；可提交订单；可查看自己的订单；可在截止时间前取消自己的已提交订单。不能进入菜品或菜单管理后台，不能查看其他员工订单，不能上传、替换或移除菜品图片，不能修改菜品、菜单价格或已生成订单。 |
| 菜品管理员 | 负责维护菜品和每日菜单的后台人员 | 可新增、编辑、上架、下架菜品；可上传、替换、移除菜品图片；可创建、编辑、发布和关闭每日菜单；可调整菜单内菜品的售罄状态。不能查看或修改员工订单，不能代替员工取消订单，不能修改系统角色或员工账号。 |

补充约束：

- 菜品管理员若同时具有员工身份，可正常下单，但不得使用管理员权限查看或修改订单。
- 角色由企业统一身份体系或公司账号目录授予，本期不建设角色管理界面。
- 员工与菜品管理员的身份、角色和数据访问权限必须在服务端校验，不能只依赖页面入口是否显示。

## 3. 范围

### 3.1 员工订餐

- 通过企业统一登录进入系统，并按角色进入对应页面。
- 查看服务日期、餐次、开放时间、截止时间，以及当前可订菜品。
- 查看菜品的名称、分类、描述、图片、单价和售罄状态；未设置图片时展示统一占位图。
- 将可订菜品加入购物车，调整数量或移除菜品，并查看订单合计。
- 提交订单，获得唯一订单号和提交结果。
- 查看自己的订单记录和订单明细。
- 在订单截止时间前取消自己的已提交订单。
- 对未登录、无权限、菜单未开放、菜品售罄、重复下单、已截止等场景给出明确提示。

### 3.2 后台菜品与每日菜单管理

- 新增、编辑菜品，设置分类、描述、参考价格、菜品图片和上下架状态。
- 上传、替换或移除菜品图片；每道菜最多一张图片，图片可选。
- 校验图片格式与大小，校验失败时给出明确提示并保留原有图片。
- 将菜品加入某服务日期、某餐次的每日菜单，并设置当餐售价和展示顺序。
- 创建每日菜单草稿，设置开放时间和截止时间。
- 发布或关闭每日菜单；发布后在截止时间到达时自动关闭。
- 将每日菜单中的菜品标记为可订或售罄。
- 保留菜品、每日菜单的最后修改人和最后修改时间。

### 3.3 数据完整性

- 订单保存提交时的菜品名称、单价和数量快照，后续菜品资料变化不得改变历史订单。
- 订单金额由服务端根据每日菜单售价快照和数量重新计算。
- 同一个员工对同一个每日菜单最多只有一个有效订单；已取消订单不占用该名额。
- 菜品图片上传、替换或移除不改变已生成订单的名称、单价、数量、金额和状态。

## 5. 业务规则与数据对象

### 5.1 核心概念

- **菜品**：可长期复用的菜品资料，包含名称、分类、描述、参考价格、可选图片和上下架状态。
- **每日菜单**：某服务日期、某餐次实际对员工开放的菜单，包含开放时间、截止时间、发布状态和该餐菜品清单。
- **菜单菜品**：菜品在某个每日菜单中的售卖记录，包含当餐售价、可订/售罄状态和展示顺序。
- **订单**：员工对某个每日菜单提交的一次有效订购，包含订单号、金额、备注、状态和菜品快照。

### 5.2 关键数据对象

#### 员工用户（User）

| 字段 | 说明 |
| --- | --- |
| `user_id` | 企业身份唯一标识，主键 |
| `employee_no` | 员工编号，可选但若存在则唯一 |
| `name` | 员工姓名 |
| `department` | 部门，可选 |
| `roles` | 角色集合，至少包含 `EMPLOYEE` 或 `MENU_ADMIN` |
| `account_status` | 账号状态，至少区分可用与停用 |

#### 菜品（Dish）

| 字段 | 说明 |
| --- | --- |
| `dish_id` | 菜品唯一标识 |
| `name` | 必填，去除首尾空格后长度为 1 至 60 个字符 |
| `category` | 必填，去除首尾空格后长度为 1 至 30 个字符 |
| `description` | 可选，最多 300 个字符 |
| `reference_price_cents` | 菜品参考单价，以人民币分表示，必须为大于等于 0 的整数 |

| `sale_status` | `ON_SALE`（上架）或 `OFF_SHELF`（下架）；新建时默认 `OFF_SHELF` |

| `quantity` | 数量，整数 1 至 99 |
| `subtotal_cents` | 单价快照乘数量 |

### 5.3 状态流转

#### 菜品

`ON_SALE`（上架）⇄ `OFF_SHELF`（下架）

- 下架菜品不能被加入新的每日菜单，也不能被员工新下单。
- 已被历史订单引用的菜品不得物理删除，只能下架。

#### 每日菜单

`DRAFT`（草稿）→ `PUBLISHED`（已发布）→ `CLOSED`（已关闭）

- `DRAFT` 对员工不可见，可修改菜单内容与时间。
- `PUBLISHED` 在 `order_open_at` 至 `order_cutoff_at` 之间对员工开放。
- 到达 `order_cutoff_at` 时系统自动将菜单置为 `CLOSED`；管理员也可提前关闭。
- `PUBLISHED` 菜单在产生首笔有效订单前可调整菜单内容与时间。
- 菜单产生首笔有效订单后，不得再修改服务日期、餐次、菜品清单和售价，只能切换菜品售罄状态或关闭菜单。
- `CLOSED` 为终态，不能再发布或恢复为可订状态。

#### 订单

`SUBMITTED`（已提交）→ `CANCELLED`（已取消）

- 只有员工本人可在截止时间前取消，取消后保留订单、菜品快照和取消时间。
- 本期不实现订单完成、退款或其他后续状态。

### 5.4 核心业务规则

- **B-01 身份与权限**：所有业务页面和数据接口都要求登录；员工只能操作自己的购物车和订单，菜品管理员不能访问员工订单数据。
- **B-02 可订条件**：只有同时满足“菜单为 `PUBLISHED`”“当前时间不早于开放时间且早于截止时间”“菜品为 `AVAILABLE`”的菜品才可加入购物车和提交。
- **B-03 菜单发布**：发布前必须至少有一个可订菜品，且截止时间必须晚于开放时间；不满足时不得发布。
- **B-04 单笔有效订单**：同一员工对同一每日菜单最多有一个 `SUBMITTED` 订单；重复提交必须拒绝。取消后可重新提交新订单。
- **B-05 金额计算**：订单总额等于所有订单菜品快照的 `unit_price_cents_snapshot × quantity` 之和，不包含折扣、税费、配送费或补贴；客户端传入的合计不得作为最终结果。
- **B-06 提交原子性**：提交时任一菜品已下架或售罄、菜单已关闭、超过截止时间或数量不合法，整笔订单失败，不得保存部分订单。
- **B-07 快照不可变**：菜品名称、参考价格、上架状态、售罄状态、菜单售价或菜单内容后续发生变化，不得改写已生成订单的快照、小计、总额、状态和下单时菜单信息；已提交订单不会因菜品下架或售罄而自动取消。
- **B-08 取消时限**：取消请求在 `当前时间 < order_cutoff_at` 时允许；在 `当前时间 >= order_cutoff_at` 时拒绝。
- **B-09 货币与时间**：金额统一以人民币分为最小单位存储，页面以元展示且保留两位小数；业务时间按 `Asia/Shanghai` 解释和展示。
- **B-10 数据保留**：已取消订单不物理删除；本期不自动清理历史订单。保留期限配置、归档和删除能力按 A-16 本期不做，正式制度后续另行确定。
- **B-11 图片管理**：菜品图片只能由菜品管理员上传、替换或移除；每道菜最多一张图片；图片为可选资料，未设置时展示统一占位图。
- **B-12 图片校验**：仅接受实际内容为 JPEG、PNG 或 WebP 且单文件不超过 5 MB 的图片；格式、大小或内容校验失败时拒绝本次图片变更，原图片和菜品其他资料保持不变。
- **B-13 图片与订单**：菜品图片不参与订单金额计算，也不进入订单快照；图片上传、替换或移除不得改变已生成订单的任何字段或状态。

## 6. 验收标准

### 6.1 访问控制

- **AC-01** 未登录访问员工订餐页或管理后台页时，系统不展示任何业务数据并跳转到企业统一登录页。
- **AC-02** 具有员工角色的用户登录后可进入订餐页，并看到当前处于开放窗口内的已发布菜单。
- **AC-03** 员工直接访问菜品管理或每日菜单管理页面时被拒绝并返回 HTTP 403，不展示任何管理数据。
- **AC-04** 菜品管理员访问员工订单列表或订单详情时被拒绝并返回 HTTP 403，不返回订单内容。
- **AC-05** 员工 A 请求员工 B 的订单详情时返回 HTTP 404，且响应中不包含员工 B 的订单号或菜品信息。

### 6.2 员工订餐

- **AC-06** 已开放菜单中的每个菜品展示名称、分类、描述（为空时可不展示内容）、单价和可订/售罄状态。
- **AC-07** 售罄菜品显示“售罄”标识，且员工无法将其加入购物车。
- **AC-08** 员工将购物车中某菜品数量从 1 改为 2 后，该菜品行小计和订单合计均准确变为原金额的 2 倍。
- **AC-09** 员工提交合法购物车后只生成一笔订单，订单具有唯一订单号，并保存提交时的菜品名称、单价和数量快照。
- **AC-10** 请求中伪造订单合计时，系统仍按菜单售价快照乘数量重新计算并保存正确总额。
- **AC-11** 同一员工对同一每日菜单已有已提交订单时，再次提交被拒绝，且原订单内容保持不变。
- **AC-12** 购物车中存在已售罄菜品时提交失败，系统中不产生该笔订单。
- **AC-13** 员工在截止时间前取消已提交订单后，订单状态变为已取消，取消时间和原订单明细仍可查询。
- **AC-14** 已取消订单不计为有效订单，员工可在截止时间前对同一每日菜单重新提交一笔新订单。
- **AC-15** 截止时间到达后，员工提交新订单被拒绝。
- **AC-16** 截止时间到达后，员工取消订单被拒绝，订单保持已提交状态。
- **AC-17** 草稿、未到开放时间或已关闭的每日菜单均不能提交订单。
- **AC-18** 菜品名称或售价发生变更后，已生成订单中的菜品名称、单价、小计和总额均保持提交时的值。

### 6.3 后台菜品与每日菜单管理

- **AC-19** 菜品管理员提交合法菜品资料后保存成功，菜品初始状态为下架，并出现在后台菜品列表中。
- **AC-20** 菜品名称去除首尾空格后为空，或参考价格为负数时，保存被拒绝且不新增菜品。
- **AC-21** 下架菜品不能被加入新的每日菜单。
- **AC-22** 下架菜品不能出现在员工的可订菜品列表中。
- **AC-23** 菜品管理员保存的每日菜单草稿对员工不可见。
- **AC-24** 菜品管理员发布包含至少一个可订菜品的每日菜单后，员工在开放时间到达时可看到该菜单及其菜品。
- **AC-25** 每日菜单没有可订菜品时，发布操作被拒绝，菜单保持草稿状态。
- **AC-26** 创建与已有菜单服务日期和餐次均相同的每日菜单时，系统拒绝保存且原菜单不变。
- **AC-27** 每日菜单产生首笔有效订单后，修改服务日期、餐次、菜品清单或售价的操作被拒绝。
- **AC-28** 每日菜单到达截止时间后自动变为已关闭状态。
- **AC-29** 员工已提交订单后，即使管理员将对应菜品标记为售罄或下架，该订单仍保持已提交状态且明细不变。
- **AC-30** 每日菜单的截止时间不晚于开放时间时，发布操作被拒绝，菜单保持草稿状态。
- **AC-31** 菜品或每日菜单每次新增、编辑后，最后修改人和最后修改时间均更新为本次操作的管理员和操作时间。

### 6.4 菜品图片

- **AC-32** 菜品管理员上传一张不超过 5 MB、实际内容为 JPEG、PNG 或 WebP 的图片并保存后，后台菜品详情展示该图片，且返回的图片地址可正常访问。
- **AC-33** 已开放菜单中的菜品若已设置图片，员工端菜品列表同时展示该菜品名称和对应图片。
- **AC-34** 未设置图片的菜品在后台和员工端均展示统一占位图，不出现破图、空白区域或原始文件名。
- **AC-35** 上传不支持的文件类型、伪装成图片的非图片文件，或超过 5 MB 的图片时，系统拒绝本次上传并给出明确提示，菜品原图片和资料保持不变。
- **AC-36** 菜品管理员替换菜品图片后，后台和员工端均展示新图片，旧图片不再作为该菜品的当前图片展示。
- **AC-37** 菜品管理员移除菜品图片后，后台和员工端均恢复展示统一占位图。
- **AC-38** 菜品图片上传、替换或移除后，已生成订单中的菜品名称、单价、数量、小计、总额和状态均保持不变。
- **AC-39** 员工调用菜品图片上传、替换或移除操作时返回 HTTP 403，且菜品图片保持不变。
